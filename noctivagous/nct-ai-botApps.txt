nct-ai-botApps

Apps like Photoshop and InDesign inherit from an earlier era.
The new generation of software developers
didn't grow up around normal, traditional software product environment
and so they tend to make UI-deficient apps that are
minimalist and ignorant of established processes that came through 
experience.  They end up redoing, in weird and inconsistent ways,
what already exist in normal ones. It would be
impossible for them to make a Microsoft Excel, for example,
given how little they know about this.  What people made in the 1980s, 1990s,
and 2000s in desktop software developed into a tradition but that
was damaged severely by the iPad and iPhone software
excitement that tried to bring touchscreen successes to desktop.  
Consequently, UI of software that needs a lot of controls is a mess: 
buttons don't have outlines or any indication that they are buttons and 
are indistinguishable from text.

Pathways

In these apps, the user doesn't really know where to start or
what to do with the app and uses it like a regular AI chat bot, 
so there should be a built-in, browsable library of categorized
stock actions, wizard templates.  Additionally, the app has to be
intentionally redesigned away from simple chat.  For example, when the user tells
the bot to do something periodically, there is no designated
place in UI where the user can review this.  The bot just says
"OK".  This indicates that the UI needs to be more developed
and we are explaining this issue here.  It should have various
sub-apps for common tasks, like budget tracking.  Since it
schedules things, it should have its own project trackers,
calendars, task lists, etc.


Establishing the User's Identity

It is never good to place the user in a forced situation 
where he or she has to go along with a charade 
and treat a robot or AI as a real person or entity
while knowing it is a charade (e.g. Clippy), at least
not at this stage of AI. But depending on how the user wants it to work
it could be valuable for the app to establish, during the setup
process, who the user is so that the bots can talk to the person
knowing the user's first name, know the email address, know
the user's cell phone number, so that the user 
can just say "call my cell" and the bot will do
that.  That is, the bots might allow different login
users with different identities, configured in Settings, 
and this could make the assistant situation more convenient.  
The key issue is whether the user trusts the AI service
with this information during use of the app.  


Widgets

Widgets here refer to the established convention of 
interactive panels and panels that show update data.
It would be valuable to have a mixture of procedurally 
updated widgets (not necessarily updated by the AI)
and stationary dashboard widgets alongside the chats.

The AI bots shouldn't be treated as chatting workers but rather
the workers behind a developed UI for interacting with them
and monitoring the status of things.

The reporting of bot activity does not have to be limited to the chat log
but can be placed outside of the chats in stationary dashboard widgets
that sit on the edge of the chat log.  In this way the bot might be
carrying out multiple tasks at once and they would be visible on
widgets rather than in the chat log.  Additionally, the bot could
spawn widgets according to the current activity and then remove them
from the side of the chat lot when they are no longer relevant. 

widgets:
   - can report on the purpose of having the app (monitoring the plants and greenhouses)
   - can report live on the activity of the bots (monitoring what the bot is doing, e.g. adjusting devices in the greenhouse)


If activity that is reflected in the widgets is transient data, not logged, so
not as exhausting for the user as following a chat log.

ui data:
   - logged: logs.  the chat log with the user, log tabs and panes that the
   bot opens up for itself.
   - transient: the live activity of what the bot is doing in real time.  can be
   logged but in the UI is transient.
       - A queue.  Let's say the bot spins up multiple subagents then
       this would be a group of queues showing the user what is
       happening.
   - monitor: the status of an external thing, e.g. a collection of data monitors 
   for measurement devices placed in a room, weather conditions, 
   vehicle location on a mini map, bank account balances, etc.

Many APIs are available to users for services they use and 
they are non-AI, procedural endpoints Then within the system that is 
an AI bot app a bot can set up a monitor widget for any of them 
upon receiving instructions from the user.


Dashboard and Control Panel Pages for Bots, Alongside Chat Log Page

	In the app, the user should be able to see
	all of what a bot has scheduled and this could be viewed
	as a gantt chart or calendar built into the app rather than
	in an external service.

	Each bot might supervise its own dashboard and control panel pages
	in addition to the dashboard and control panel pages that exist at the app level.
	The control panel page would allow the bot to set up buttons
	that the user can click as well as forms (that it can make)
	where the user can enter the data and the bot receives
	the command.  This is another avenue to interacting with
	the bot outside of typed commands.

   other pages:
   	- gantt charts, task lists, address book, etc.
   
   The bots should have access, when desired, to an individual or global
   calendar, gantt chart, kanban, task lists, contacts, etc. rather than
   relying on "connectors" to external services, or at least
   using synced data from them and using the app's own modules.  
   e.g. it should have built in email client
   so that the user can tell the bot to open up the email client
   app (inside a webview tab of the app), the user can edit.
 

global app level.

	monitor modules - get callbacks, send to bots.
		- global resource module.  e.g. remote database, email acct.
	    - will be known by all of the bots ahead of time
	    - can be connected to individual bots by user.
	    

	individual bot level: 
			stationary UI next to the chat.
		  	- dashboard feature - for individual items to monitor. e.g. a dashboard with different
		  greenhouse and plant monitor widgets.
			- email widget that shows the email box that the bot controls.

		 web views
		   - bots should open up web pages within web view tabs inside the app
		   window instead of opening external web browser.
		   
		   
The Setup of The App And Its Capabilities

There are two major sides: the setup of the app
and its capabilities.  The setup refers to that it can
put things in the cloud for scheduling even if the app
is closed.  The capabilities means what it can do.
If the user doesn't have access to either, then there will
be not only an unnecessary period where he or she has
to find these things out but also an added overall strain to the
user experience.  Then with the capabilities, if
they are available but hardly revealed in the UI,
then the user will struggle to use it, always having
to recall what the app can do.   If there are tasks
that the user wants to do but have been done by
others then those should exist as template workflows 
and wizards, like collecting bill and budget information.

It's worth noting also, that in a chat log, the chat responses
from the AI could in theory be annotated on the side.
